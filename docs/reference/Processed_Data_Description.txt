HILL OF TOWIE WIND FARM - PROCESSED DATA DESCRIPTION
Folder: data/00-Processed-Data
==============================================================================

1. WHAT IS IN THE FOLDER
------------------------------------------------------------------------------
14 files, one pair per year:

  turbines_YYYY.xlsx           the cleaned 10-minute SCADA data (one workbook/year)
  turbines_YYYY.cleaning.json  a log of what the cleaning step removed

Years available: 2018, 2020, 2021, 2022, 2023, 2024, 2025.
There is NO 2019 file. The 2018 file starts on 1 March 2018 and the 2022 file
starts on 4 April 2022 at 10:40. All the others cover the full calendar year.

Note: the unprocessed folders here (2016-2019) are NOT the source of these
files. The cleaning logs show the xlsx files were made from a separate export
(ENGG2112-T3-G7\data\interim\turbine_exports\turbines_YYYY.xlsx). Only 2018
overlaps with the raw data in this folder.

Data source: Hill of Towie wind farm open dataset (Zenodo record 14870023),
21 turbines, 10-minute SCADA averages plus an alarm log.


2. HOW EACH WORKBOOK IS LAID OUT
------------------------------------------------------------------------------
- One worksheet per station, named  Station_<StationId>.
    Station_2304510 ... Station_2304530  = the 21 turbines (T01-T21 in order)
    Station_91                            = site-level station (not a turbine).
                                            It is EMPTY (header row only) in
                                            every year, and missing from 2020.
- Row 1 is the header and the top row is frozen. Every following row is one
  10-minute interval for that turbine.
- Rows are in ascending time order. There are no duplicate timestamps, and
  consecutive rows are exactly 600 s apart except where rows were removed by
  cleaning (see section 5).
- 2018, 2020, 2021: 45 columns.
  2022-2025: 47 columns (two extra temperatures, wtc_InvUpTmp_mean and
  wtc_TrafoTMa_mean, which the cleaning step removed from the earlier years).
- Apart from the two alarm columns, every cell in every kept row is filled
  (0 missing values were found). The alarm columns are blank unless an alarm
  happened in that row.
- Storage quirk: TimeStamp and StationId are stored as TEXT, not as an Excel
  date or number. Convert them after loading, e.g. in pandas:
      df["TimeStamp"] = pd.to_datetime(df["TimeStamp"])
      df["StationId"] = df["StationId"].astype(int)
- The files are large (340-485 MB, about 21-22 sheets of ~52,000 rows each).
  pd.read_excel(path, sheet_name=None) works but is slow. Loading once and
  saving to parquet/CSV saves a lot of time later.

Row counts per year (all turbines combined):

  Year  Sheets  Period covered                         Rows        % of full 10-min grid*
  2018  22      2018-03-01 00:00 -> 2019-01-01 00:00     919,106   99.3 %
  2020  21      2020-01-01 00:00 -> 2021-01-01 00:00   1,101,294   99.5 %
  2021  22      2021-01-01 00:00 -> 2022-01-01 00:00   1,090,804   98.8 %
  2022  22      2022-04-04 10:40 -> 2023-01-01 00:00     778,694   94.8 %
  2023  22      2023-01-01 00:00 -> 2024-01-01 00:00   1,098,422   99.5 %
  2024  22      2024-01-01 00:00 -> 2025-01-01 00:00   1,102,885   99.6 %
  2025  22      2025-01-01 00:00 -> 2026-01-01 00:00   1,059,412   96.0 %
  * 21 turbines x every 10-min step in the period.

Each year file includes the 00:00 timestamp of 1 January of the NEXT year as its
last row, so for a full year one turbine has 52,561 slots (52,705 in a leap year).
Watch for this boundary row if you concatenate years.
Per-turbine row counts are typically 50,000-52,700 for a full year. The lowest
are 2304529 in 2021 (43,378) and 2304520 in 2022 (35,840 of a possible 39,105).


3. COLUMN DICTIONARY
------------------------------------------------------------------------------
Naming convention: wtc_<Tag>_<statistic>
  wtc_      = wind turbine controller signal
  _mean     = average over the 10-minute interval
  _stddev   = standard deviation within the 10-minute interval
  _endvalue = value at the end of the 10-minute interval
The raw tables also have _min / _max, which were not kept.

[O] = description from the official field dictionary
      (Hill_of_Towie_turbine_fields_description.csv)
[I] = NOT in the official dictionary. The meaning is my interpretation of the
      tag name and value range; treat it as a best guess.

Range = min / max / mean across all turbines and all years in the processed data.

Note on TimeStamp: every alarm event kept in the file has TimeOn exactly equal to
its row's TimeStamp. Each file runs from 00:00 on 1 Jan to 00:00 on 1 Jan of the
next year. The official dataset does not say whether a timestamp marks the
start or the end of its 10-minute window. If that matters to your features,
check against tblSCTurbine's wtc_CurTime_endvalue column in the raw data.


4. VALUES TO WATCH OUT FOR (likely sensor fault or limit codes)
------------------------------------------------------------------------------
- Exactly 200 and -50 degC turn up in several temperature channels (HS/IMS
  gearbox bearings, gear oil, Gen1U1, A9, DeltaTmp, brake). They are almost
  certainly sensor-limit or fault values, not real temperatures. They appear in a
  handful of turbine-years (e.g. 2018: 7 turbines hit 200 on the gearbox
  bearing channels).
- Exactly -100 bar appears in HydPress / HubPresA-C (2021-2025) and is almost
  certainly a fault value.
- A1ExtTmp reaches 251.6 in 2020 and TraOilTF reaches 154.8 in 2020. Both are
  implausible spikes.
- Zeros are common when a turbine is stopped (rpm = 0, pressures near 0,
  PowerRef = 0). They are real readings, not missing data.
- Hydraulic and hub pressures of ~230 bar are the NORMAL operating level.

Consider masking or clipping these before training, and checking them against
the alarm log, since a sensor fault can itself be an alarm.


5. WHAT THE CLEANING STEP DID (from turbines_YYYY.cleaning.json)
------------------------------------------------------------------------------
Each JSON has:
  "source"           path of the pre-cleaning export the xlsx was made from
  "removed_columns"  columns dropped entirely
                     (2018/2020/2021: wtc_InvUpTmp_mean, wtc_TrafoTMa_mean; 2022+: none)
  "required_columns" the 43 (2018-21) or 45 (2022-25) columns a row had to have
                     filled to be kept: StationId, TimeStamp and the sensor columns
  "sheets"           per station: input_rows, kept_rows, removed_rows,
                     alarm_events_in_removed_rows

Totals per year:

  Year   Input rows   Kept rows   Removed rows   Alarm events in removed rows
  2018    1,889,881     919,106       970,775        808,142
  2020    1,753,452   1,101,294       652,158        663,111
  2021    1,872,881   1,090,804       782,077        797,861
  2022    1,448,981     778,694       670,287        416,216
  2023    1,429,407   1,098,422       330,985        346,231
  2024    1,416,602   1,102,885       313,717        328,955
  2025    1,437,782   1,059,412       378,370        396,222

So a row was kept only if every required sensor column had a value.


6. IMPORTANT CAVEAT FOR ALARM PREDICTION: MOST ALARMS WERE DROPPED
------------------------------------------------------------------------------
The alarm columns in these files contain very few events:

  Year   Rows with an alarm   Alarm events kept
  2018         1,306                1,331
  2020         1,203                1,214
  2021         1,505                1,508
  2022           591                  619
  2023           700                  715
  2024           747                  771
  2025         2,371                2,832
  Total                             8,990

For comparison, the raw tblAlarmLog for March-December 2018 has 706,572 events,
and the processed 2018 file keeps 1,331 of them (about 0.2 %).

Why: every kept event has a TimeOn of exactly HH:M0:00, the same as its row's
TimeStamp. The pre-cleaning export appears to have put each alarm on its own row
at its own timestamp (which is why input_rows is roughly double the 10-minute
grid). Those alarm-only rows had no sensor values, so cleaning removed them
(the "alarm_events_in_removed_rows" counts above). Only alarms that happened
exactly on a 10-minute boundary survived.

Also: 128 distinct codes appear in the processed files. Codes 20 and 25 (generator
cut-in / cut-out) make up most of what is left. Rarer fault codes are mostly
gone.

To use alarms as labels, re-attach them from the raw tblAlarmLog: floor each
TimeOn to its 10-minute interval (or label a look-ahead window), and join on
StationId + TimeStamp. Don't rely on the Alarmcode / AlarmEvents columns here.
See Alarm_Codes.txt for the full code list.


7. QUICK LOAD EXAMPLE (pandas)
------------------------------------------------------------------------------
    import pandas as pd, json
    sheets = pd.read_excel("turbines_2023.xlsx", sheet_name=None)   # dict of DataFrames
    sheets.pop("Station_91", None)                                   # empty sheet
    df = pd.concat(sheets.values(), ignore_index=True)
    df["TimeStamp"] = pd.to_datetime(df["TimeStamp"])
    df["StationId"] = df["StationId"].astype(int)
    df["events"] = df["AlarmEvents"].dropna().map(json.loads)        # list of dicts or NaN
