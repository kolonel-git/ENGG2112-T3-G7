# Single-year baseline evaluation

## Purpose and running

`scripts/single_year/run_year_baselines.py` evaluates constant and random scores
within one year, defaulting to **2018**. These are reference baselines, not trained
sensor-based models. They need the episode and label files from `build_labels.py`;
they do not read the feature table.

From the repository root, using the Python environment with the dependencies installed:

```powershell
python scripts/single_year/run_year_baselines.py
python scripts/single_year/run_year_baselines.py --year 2018 --resamples 100
```

Change `YEAR` in the script or use `--year`. Default results are written to
`reports/tables/baselines_dummy_cv_2018.csv` (the selected year appears in the name).
Rerunning replaces that CSV. The main `baselines_dummy.csv` is separate.

## Targets and labels

- **A:** episodes derived from daily recorded fault duration (`TimeErr`).
- **B:** episodes derived from sustained low generator speed with sufficient wind.

Both use the existing labels, coverage exclusions, and episode definitions from
`configs/protocol.yaml`. A positive day precedes an episode start in the next
30 days. Days already in an episode, days in the 31–60 day exclusion zone, and
other unusable days do not receive scores. A negative day satisfies the existing
observation and exclusion rules. No labels are regenerated by this runner.

## Chronological folds

All turbines use the same date boundaries. Each fold calibrates a threshold on
earlier labelled days, then freezes it for later test days:

| Fold | Test block (end exclusive) | Scored test days before label/coverage exclusions |
|---|---|---|
| 1 | April 1 – July 1 | April 1–May 1 |
| 2 | July 1 – October 1 | July 1–August 1 |
| 3 | October 1 – January 1 of the next year | October 1–November 1 |

These dates use the current 60-day full label horizon. Calibration requires
`Day + 60 days < test block start`. Test scoring requires
`Day + 60 days < test block end`. The rest of each block supplies outcome
follow-up rather than additional scored days. Calibration expands across folds;
past test periods can subsequently become calibration data once their horizons
are complete. Test days never overlap between folds. Empty folds are skipped
with a message; if all are empty, no results file is written.

This tests time separation within a year, using the same turbine population.
It does not hold out turbines or measure transfer to a different year/site.

## Scores and alert threshold

**Constant (prevalence):** every row gets score zero. The name describes its
average-precision reference value, not a fitted probability. Tied scores rank
all days equally. With the usual selected threshold of zero, it issues no alerts.

**Random uniform:** each row gets a random score between zero and one, independent
of sensor data and outcomes. There is one random-score realisation per target
and fold, seeded reproducibly. Three folds times two targets produce six random
rows and six constant rows when every fold is evaluable.

An alert occurs when `score > threshold`, strictly. The threshold is selected
on calibration rows to satisfy the configured false-alarm budget, currently
one false alarm per turbine-month. Ties are kept together. A threshold of
`-inf` means alert on every row. The threshold is not adjusted using test labels.
The test false-alarm rate can exceed the calibration budget.

## Metrics

| CSV column | Definition and interpretation |
|---|---|
| `n_rows` | Number of scored turbine-days in this test fold, across turbines. |
| `n_positive_rows` | Number of scored days with label 1. |
| `prevalence` | `n_positive_rows / n_rows`. A context statistic, not prediction skill. |
| `pr_auc` | Scikit-learn average precision: the sum of precision at each recall increase, weighted by that increase. It assesses ranking without using the alert threshold. Higher is better; the constant-score reference equals prevalence. It is not the trapezoidal area under an interpolated curve. |
| `n_episodes` | Episode starts in the test block with at least one scored day in their preceding 30-day warning window. Episodes without scored warning days are excluded from this denominator. |
| `n_detected` | Evaluable episodes with at least one alert in that warning window. |
| `recall` | `n_detected / n_episodes`. This is episode recall, not the fraction of positive rows alerted. Higher is better at a comparable false-alarm rate. |
| `median_lead_days` | For each detected episode, take the earliest alert in its warning window and count days until the episode starts; report the median across detected episodes. Undetected episodes do not contribute. Larger means earlier warning, but interpret alongside recall and false alarms. |
| `false_alarms_per_turbine_month` | Count alerted rows labelled 0, divided by `n_rows / days_per_month` (currently 30.4375). Exposure includes all scored rows. Each alerted negative day counts separately; alerts are not merged into incidents. Lower is better at a comparable recall. |

Example: 10 false alerts across 609 scored turbine-days give
`10 / (609 / 30.4375)`, approximately 0.50 false alarms per turbine-month.
Detecting 17 of 30 evaluable episodes gives recall `17 / 30`, approximately 0.567.

Average precision is undefined without positives; recall is undefined without
evaluable episodes; lead time is undefined without detections. These appear as
blank CSV cells (NaN), not zero. Empty scored frames cannot be evaluated.

## Confidence intervals and identifying columns

Each of the four metrics (`pr_auc`, `recall`, `median_lead_days`, and
`false_alarms_per_turbine_month`) has `_lo` and `_hi` columns. They are percentile
bootstrap bounds, currently 95%, obtained by resampling whole turbines with
replacement. The threshold and random scores stay fixed during resampling.
Undefined bootstrap draws are omitted for that metric; no valid draws produce
blank bounds. Default draw count is configured in `protocol.yaml`; `--resamples`
overrides it for this run.

These intervals describe variation under turbine resampling, conditional on this
year, fold, and score realisation. They do not quantify variation across random
seeds, years, or newly trained models. The same random scorer is not retrained
for each bootstrap draw.

| Column | Meaning |
|---|---|
| `year` | Selected calendar year. |
| `target` | A or B, as defined above. |
| `fold` | Chronological test-block number, 1–3. |
| `test_block_start` | Inclusive test-block start. |
| `test_block_end_exclusive` | Exclusive test-block end, including reserved follow-up time. |
| `calibration_rows` | Earlier labelled turbine-days used to select the threshold. |
| `purge_days` | Full label horizon used for temporal separation. |
| `model` | Constant or random score generator. |
| `threshold` | Frozen calibration threshold applied to test scores. |

## Reading the results responsibly

A random scorer can detect many episodes because it has multiple opportunities
to alert in a 30-day window. High recall alone is not evidence of predictive
skill. Compare recall with the false-alarm rate, lead time, prevalence, and
average precision. Test class balance and thresholds vary between folds.

The output contains per-fold results rather than a pooled CV estimate. Averaging
fold medians or average precision values does not produce the corresponding
pooled metric. Missing dates and excluded labels further limit coverage.

The runner reuses labels built upstream, including their original split and
censoring rules. It does not establish performance outside 2018 or replace the
main held-out-year experiment. The implementation of the shared metrics is in
[`metrics.py`](../../src/wt_predmaint/evaluation/metrics.py).
